\chapter{Progettazione dell'architettura}\label{chapter:architettura}
\section{Preambolo sulle scelte architetturali}
Le scelte archittetturali sono dipese in primo luogo dall'infrastruttura aziendale,
e successivamente dalle richieste durante gli incontri.
L'utilizzo di SQLServer, come motore di database, è stato preso come base di tutte le scelte successive.
Da questo caposaldo, si è proseguito con la ricerca di un framework che interagissero sia con SQLServer che SQLite.\cite{SQLite}.
La necessità di operare offline ha guidato la ricerca di
 un sistema installabile in locale, escludendo così le soluzioni web based.
La scelta è quindi ricaduta sulla piattaforma \dotnet\cite{DotNet} con linguaggio 
\csharp{} che, in quanto dell'ecosistema Microsoft,
è perfettamente integrata con i database prima citati.
La piattaforma \dotnet{} è espandibile mediante l'utilizzo di \nuget{}\cite{NuGet},
che permette di aggiungere package e quindi funzionalità al progetto.
 I pacchetti sono sviluppati sia da Microsoft che da terze parti,
e vengono aggiornati e supportati continuamente.
 Questa manuntenzione continua evita di incorrere in debiti tecnici futuri.
L'ambiente \dotnet{} è nativamete multipiattaforma, questa proprietà soddisfa le necessità dei richiedenti.
Secondo le linee guida Microsoft, per lo sviluppo delle view multipiattaforma,
è consigliato l'utilizzo del package \nuget{} \dotnet{} \texttt{MAUI}\cite{MAUI}.
In fase di compilazione, \texttt{MAUI} converte il codice sorgente in codice nativo per la piattaforma di destinazione.
\texttt{MAUI} integrato con il package \nuget{}  ``Comunity Toolkit Maui''\cite{ComTolkit} consente la possibilità
 di costruire le interfacce grafiche in codice \csharp.
  Nativamente \texttt{MAUI} supporta solo il linguaggio Markup \xaml\cite{XAML}.
\section{Deployment}
La scelta degli ambienti di sviluppo prima citati, porta a dover considerare il deployment dell'applicativo.
Il software verrà installato in locale su ogni dispositivo, sia esso desktop o mobile,
e si connetterà al database centrale.
All'interno dell'azienda è presente un dominio \ac{AD}, dove ogni Oggetto del dominio ha un \ac{IP} statico.
Questa configurazione permette la connessione al database, risiedente in un server all'interno del dominio,
in modo agile tramite \ac{IP}, se si è connessi all'interno della \ac{LAN}.
Lo scambio di dati tra il frontend e il backend avviene mediante protocollo \ac{TCP/IP}.
Si è valutato, per chi accede dall'esterno del dominio, di utilizzare la rete \ac{VPN},
stabilendo una connessione virtuale che permette di essere all'interno della \ac{LAN}.
Il database locale, in SQLite, è strutturato come una copia del database centrale.
I dati vengono sincronizzati tra i due database mediante un processo di sincronizzazione.
In assenza di connessione, verificabile tramite ping, si accede al database locale, e
ristabilita la connessione, i dati vengono sicronizzati.

Nella fase di sviluppo, per testare la struttura del database,
 è stato scelto di utilizzare una versione di SQLServer locale, denominata SQL Express\cite{SQLExpress}.
SQL Express condivide con SQL Server tutte le caratteristiche principali,
 questa proprietà ha permesso di costruire query e testare funzionalità localmente, ma compatibili
 con il database di produzione.

\section{Package}
L'intero software è stato suddiviso in tre distinti package, con resposabilità diverse.
Si è cercato di seguire il principio \ac{DRY} e la riusabilità degli stessi.
\subsection{Interfaccia al database}
Il package di interfaccia al database, denominato ``DatabaseManagementPackage'',
ha il compito di gestire tutti gli aspetti legati a quest'ultimo, come:
\begin{itemize}
    \item Gestione connesioni ai vari database, come SQLite e SQL Server o, nel caso dei test SQL Express.
    \item Gestione delle transazioni.
    \item Gestione dei permessi utente, bloccando le operazioni non consentite.
    \item Conversione, medinte \ac{ORM}, delle tabelle database in entity.
    \item Mappare entity in file neutri, proteggendo il database.
    \item Gestione di Repository per ogni entità, che espongono le operazioni \ac{CRUD}.
    \item Gestione di una suite di test per verificare le operazioni precedenti.
          Questa suite è risultata fondamentale nell'evoluzione del database,
          validando i cambiamenti apporatti al database.
    \item Esporre al di fuori del package solo file neutri e classe di manager del database.
\end{itemize}
Nella implementazione si è utilizzato il pacchetto \nuget \ac{EF Core}\cite{EFCore}.
Questo modulo permette una gestione efficiente delle operazioni di accesso ai dati,
consentendo di astrarre le tabelle del database in classi di entity.
Le entity sono state a loro volta mappate in \ac{DTO}, proteggendo i dati.
Questa seconda mappatura è stata realizzata mediante il package ``Mapster''\cite{Mapster},
appartente a terze parti. 
La mappatuta entity-\ac{DTO} è stata realizzata in modo bidirezionale in quanto, in alcuni casi,
è necessario convertire un \ac{DTO} in entity per poterlo salvare nel database.
\subsection{Libreria di componenti View}
La creazione di interfacce grafiche è stata supportata dalla creazione di un package dedicato,
che racchiude in sè factory di componenti, costanti e utilità.
Il package, denominato ``ViewComponentLibrary'', è stato concepito a sé stante
per favorire un suo impiego in implementazioni future.
La libreria si appoggia a sua volta al package \nuget{} ``Comunity Toolkit Maui''\cite{ComTolkit}.
Questo package permette di scrivere le interfacce grafiche in codice \csharp{} Markup,
evitando quindi l'utilizzo del linguaggio \xaml\cite{XAML}, standard di sviluppo per le interfacce MAUI.
\subsection{Modulo Main e View}
Il package principale, ed il main del progetto, è quello dedicato all'orchestrazione dei componenti
e alla gestione dei flussi di lavoro.
Il package, denominato ``ConfiguratoreCommerciale'', ha numerosi compiti,
tra cui la gestione della Dependency Injection, la creazione delle view e dei rispettivi ViewModel.
In questo package risiedono infatti i ViewModel, che si interpongono tra le view e i repository,
esponendo i dati tramite ``Observable Properties''.
Le Dependency Injection invece permettono di iniettare
le dipendenze necessarie alle classi, come ad esempio i repository, classi di Logging o le view stesse se registrate.
Le classi di view, utilizzando i componenti della libreria,
vengono realizzate tenendo conto del dispositivo di destinazione.
La differenziazione è permessa dall'utilizzo di compilazione condizionale,
distinguendo il codice da compilare in base alla piattaforma di destinazione.
Un esempio di tale condizione è il seguente:
\begin{lstlisting}[language=CSharp]
#if ANDROID
    // codice per piattaforma Android
#elseif WINDOWS
    // codice per piattaforma Windows
#endif
\end{lstlisting}
Questa possibilità permette anche di eseguire parti di codice in solo in fase di DEBUG.
Gli aspetti generali gestiti dal package possono essere riassunti come segue:
\begin{itemize}
    \item Creazione interfacce grafiche.
    \item Traduzione a compile time della conversione di codice \csharp{} in \xaml{}.
    \item Traduzione a compile time in elementi nativi per la piattaforma di destinazione.
    \item Gestione delle interfacce mediante ViewModel,
          che a loro volta tramite observable modificano la view in risposta ad eventi.
    \item Gestione della navigazione tra le interfacce grafiche.
    \item Gestione dei permessi, mostrando solo i comandi che competono al ruolo dell'utente.
    \item Mediante la classe MauiProgram.cs gestione della Dependency Injection.
    \item In fase di avvio creazione di una cache in RAM di dati immutabili durante la sessione, come tabelle di lookup.
\end{itemize}
